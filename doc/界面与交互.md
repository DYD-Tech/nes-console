# 界面与交互

屏幕内那台「游戏机系统」怎么摆、怎么响应。色板数值与对比度实测在 [`color.md`](color.md)，
每条坑的「现象 → 原因 → 做法」在 [`值得记住的坑/nes-console.md`](值得记住的坑/nes-console.md)。

## 画面最大化

NES 的原始分辨率是 256×240，但当年的游戏美术是按 **4:3** 的非方形像素设计的
（CRT 电视的像素不是正方形），所以画面要拉伸成 4:3 显示，圆形道具才不会变形。

画面是 4:3，而屏幕比例五花八门，所以画面铺满一屏后**必然在某个方向留下余量**：
宽屏（16:9 等）左右有余量，竖屏（手机）下方有余量。

如果让界面跟画面上下分屏，界面就会吃掉画面高度（实测吃掉 216~268px，占屏高 20%~30%）。
所以**界面做成屏幕内的一层**（对标 RetroArch Ozone：菜单直接画在画面里），
画面因此能吃到理论最大值 —— 即「视口内能放下的最大 4:3 矩形」。
画面之外只剩触摸手柄和摆放模式提示条，其余（菜单、菜单按钮、底部那一栏提示）都在屏幕里。

余量落在哪里，决定了手柄怎么摆、会不会压到画面（由 `test-canvas-sizing.cjs` 逐档量过）：

| 场景 | 视口比例 | 余量位置 | 手柄遮挡画面 |
|------|----------|----------|--------------|
| 宽屏（16:9、21:9） | > 8:5 | 左右两侧 | 不遮，两块按键组分列两侧 |
| 竖屏（手机、平板竖屏） | ≤ 4:3 | 下方 | 不遮 |
| 比例接近 4:3（1024×768、1440×900） | 4:3 ~ 8:5 | 没有余量 | 必然叠加，可在「控制管理」里把手柄设为隐藏 |
| 横屏手机且两侧很窄（667×375） | > 8:5 | 左右，但比一块按键组还窄 | 必然压到画面边缘，用「自由摆放」挪位置 |

关键实现（细节见 `src/styles/global.css` 的注释）：

- 画面尺寸用容器查询单位表达：`width: min(100cqw, calc(100cqh * 4 / 3))`
  配 `aspect-ratio: 4/3`，宽度恒不超过容器宽、高度恒不超过容器高
- 手柄用**绝对定位**贴在视口下沿，所以它占多大都不影响画面尺寸；
  竖屏时改贴「画面下方那块余量」的下沿
  （余量 = 视口高 − 画面高 = `100cqh - min(75cqw, 100cqh)`）：
  普通手机抬到离底边 180px（拇指的自然落点，也躲开系统手势条），
  近正方形这类余量很薄的窗口自动退回贴底，优先保证不压画面
- **手柄有多大 = 一把尺子 `--pad-u`（三档 16 / 19 / 22px，窄屏按视口宽封顶）**，
  画面给手柄让位的那两个数（抬升 12.7u、常态 11.7u）读的是同一把尺子，
  所以换档位时画面跟着让，不会出现「键变大了、还压在画面上」。账见 `doc/控制与手柄.md`
- **竖屏常态画面离顶边 8px**，不垂直居中：居中会把余量平分到上下两半，
  而手柄是按「整个下方区域」底部定位的，结果手柄会压住画面下半部分
- **背景台**：`.stage` 用中性石墨渐变 + 极淡网格，整页只有一个色相（强调青）；
  屏幕内是 Ozone 的灰 + 青，外围不自带一套颜色跟屏幕里抢
- **屏幕边框**：`.screen` 有 3px 深色边框 + 12px 圆角 + 多层阴影
- 高度用 `dvh`（动态视口高度）而非 `vh`：移动端浏览器地址栏显隐时 `vh` 会让内容被遮挡
- **不使用** `object-fit: contain`：它会保住 canvas 固有的 256:240（16:15），
  左右留黑边，恰好破坏要的 4:3 拉伸效果
- **画面容器的祖先必须用 `height` 而不是 `min-height`**：`cqh` 要求容器高度「确定」，
  用 `min-height` 时高度不确定，`cqh` 会解析成 0，画面会消失

实测（`agent-workspace/test-canvas-sizing.cjs`，16 种分辨率全过，都达到理论最大）：

| 分辨率 | 画面尺寸 | 余量位置 |
|--------|----------|----------|
| 手机竖屏 390×844 | 390×293 | 下方 |
| 手机横屏 844×390 | 520×390 | 左右 |
| 平板竖屏 768×1024 | 768×576 | 下方 |
| 笔记本 1366×768 | 1024×768 | 左右 |
| 桌面 1920×1080 | 1440×1080 | 左右 |
| 2K 2560×1310 | 1747×1310 | 左右 |
| 4K 3840×2030 | 2707×2030 | 左右 |

## 菜单导航：焦点模型

1. 页面加载后，屏幕内显示主菜单（游戏 / 游戏管理 / 控制管理 / 系统 / 操作说明 / 关于）
2. **菜单里的焦点分「分类栏」和「列表」两处，一次只在一处**，方向键按直觉走
   （`screen-ui.js` 的 `handleAction`；对标 RetroArch Ozone 的键分发：`MENU_ACTION_LEFT`
   进侧栏、`RIGHT` 或 `OK` 出侧栏回列表、`SCROLL_UP/DOWN` 只动当前那一栏）：

   | 焦点在哪 | ↑ ↓ | → 或 A | ← 或 B |
   |----------|-----|---------|---------|
   | 分类栏 | 换分类 | 进入该分类的列表（光标停在第一行） | 回退一层 / 顶层则关闭菜单 |
   | 列表 | 换条目 | 确认当前条目 | 回到分类栏 |

   左右不被当成「在两栏之间横跳」—— 两栏本来就是上下排的。进出的位置都记着
   （离开分类栏再回来还在原来那个分类，回列表还在上次那一行）。
   与 Ozone 的唯一不同：手机右手拇指只有 A/B，所以在列表里按 **B 也是回分类栏**，
   不是直接退一层（Ozone 在列表里按 CANCEL 是返回上级）。
3. **高亮框只画在当前焦点那一项上**（`.sys-ui[data-focus]` 门控）。分类栏失焦后仍保留
   深色底和青绿文字，所以「当前是哪个分类」始终看得出来，只是不再和列表里那一个框抢视线。
4. 光标停在哪一行，右侧详情栏就显示那一行的信息（目前只有存档的槽位列表用这块栏子）。
   窄屏（容器 ≤ 420px）放不下两栏并排，详情栏改到列表**下面一行**，
   靠 `.sys-body:has(> .sys-detail:not([hidden]))` 切成上下排 —— 这里不能用 `flex-wrap`，
   换行的 flex 容器不会把超高的那一行收缩回来，整块会被撑到屏幕外。
5. 只有一个分类的菜单（游戏内快速菜单、存档槽位列表、槽位操作、各种确认屏）**没有分类栏**，
   焦点直接落在列表上；这时 ←→ 归还给「调数值」（左减右加，A 递增到顶回到最小）。
6. 选中游戏按 A 启动；游戏中按右上角「菜单」（或 Esc / SELECT+START）呼出快速菜单；
   快速菜单里可存档 / 读档 / 进设置 / 退出到主菜单。菜单里按 B 逐级返回，
   在最顶层的分类栏按 B 关闭菜单回到游戏。

侧栏的顺序就是使用频率（游戏 → 管理 → 控制 → 系统 → 说明 → 关于）。
窄屏（容器 ≤ 420px）侧栏**照样竖排**、占 36% 宽，六个分类放不下就上下推且不露滚动条；
手机上不把它们横过来当顶部标签，因为分类的位置本身就是信息（第几项＝第几个分类）。
焦点在分类栏时按 ↑↓，当前那一项会自动滚进视野（`_renderSidebar` 里一句 `scrollIntoView`），
不存在到不了的分类。

## Ozone 配色

屏幕内的系统界面配色**直接取自 RetroArch 源码**，不是凭印象配的。
来源：`menu/drivers/ozone.c` 的 `ozone_theme_dark`（第 1220 行），
默认主题由同文件 9817 行 `ozone->default_theme = &ozone_theme_dark` 指定。
完整色值表见 [`color.md`](color.md)，两个容易做反的地方：

1. **选中项比底色暗**。多数现代 UI 把选中行提亮，Ozone 反过来：填充 `#212227`
   比底色 `#2D2D2D` 更深，靠青色描边 + 青绿文字凸显。提亮就不像 Ozone 了。
2. **游戏中菜单半透明**。`ozone_set_background_running_opacity()`（ozone.c:1941）注明
   `framebuffer_opacity` 默认 0.900 时背景顶部 alpha = 1.0、底部 alpha = 0.75，
   所以呼出菜单能看到后面的画面、越往下越透 —— 这是 Ozone「不打断游戏」的观感来源。
   本实现按同样的公式取值。

色板变量定义在 `.screen` 上而不是 `.sys-ui` 上：屏幕里用这套色的不止菜单本体，
菜单按钮和 toast 在菜单关闭时也得显示，而 `.sys-ui` 一 `hidden` 整个子树都没了，
所以定义在三者的共同祖先上，一处取值、三处同步。屏幕外是另一套（石墨 + 强调青），
两边的青也不同值 —— Ozone 的青是选中框的 `#2DA3CB`，外围的 `#7FD8F5` 要压在近黑底上仍然显眼。

一处有意增强：游戏中菜单加了 `backdrop-filter: blur(2px)`（Ozone 没有这个），
因为网页上的游戏画面动得快，纯叠加会让文字难读。

## 菜单打开时暂停游戏

打开任何菜单（主菜单、快速菜单、设置、存档管理、游戏信息）都会暂停游戏，关闭后自动继续。
对标 RetroArch：`runloop.c:3516-3521` 在菜单打开时把核心标记为暂停
（`core_paused` → `RETRO_THROTTLE_FRAME_STEPPING`），由配置项 `menu_pause_libretro`
（界面里的「Pause Content When Menu Is Active」）控制，默认开启。本实现同样默认暂停。

实现分工：

- `NesConsole.pause()` —— 停帧、松开所有按住的按键、清空音频队列。
  和 `stop()` 的区别是音频上下文保持活着，恢复时接着跑，不用重新加载 ROM。
- `ScreenUI` 的 `onOpen` / `onEmpty` 回调 —— 「从关着变开着」通知暂停，「从开着变关着」通知恢复。
  边界判断在界面层，所以菜单从哪个入口打开都走同一条路径，不会出现「某个入口忘了暂停」。
- `app.js` 的 `pauseGame()` / `resumeGame()` —— 顺带停/启计时器、弹一条 toast。

两个约束：**暂停时必须松开按住的按键**（暂停期间按键被界面消费，游戏收不到松开事件，
那些键会一直保持按下；所以松开动作写在 `pause()` 里，它是暂停语义的一部分，
不能指望每个调用方记得调）；**不要用 `audioCtx.suspend()` 静音**（它是异步的，
快速开关菜单时两次调用的 Promise 可能乱序完成，表现为恢复后没声音。
改成「停止跑帧 + 清空音频队列」，效果一样但没有竞态）。

还有一个时间窗：**载入期间按 MENU**。`pauseGame()` 和 `toggleMenu` 都看 `playing`，
而这个标志要等「下载 ROM → 编译 wasm → `loadROM`」这几秒走完才置真，
那期间按 MENU 既不暂停、呼出的还是主菜单；核心却是 `loadROM` 内部自己 `start()` 的，
一结束就在菜单背后跑起来。所以 `startGame()` 在置好 `playing` 之后补一次检查：
菜单还开着就立刻 `pauseGame()`。

验证（`verify-pause-on-menu.cjs`）看核心自己数的帧（`host.frames`）在 900ms 窗口里的增量：
游戏中约 54 帧、菜单打开（含子菜单）0 帧、关闭又回到约 54 帧，
另有一段专门走「按下启动→立刻呼出菜单」这条路，钉住上面那个时间窗。
**不能靠「画面变不变」判断**：游戏停在标题画面时画面本来就是静止的，那样测会得到假阴性。

## 屏幕右上角的两颗常驻按钮

最右那颗写着中文「菜单」，它左边一颗是全屏图标（`.touch-fs`）。两颗同一排、同尺寸、同形状。

| 游戏状态 | 外观 | 按一下 |
|----------|------|--------|
| 游戏中（菜单关闭） | 略透的深底小圆角方块 | 呼出菜单 / 铺满屏幕 |
| 菜单打开 | 不透明的小圆角方块 | 关闭全部菜单，回到游戏 / 退出全屏 |

### 颜色为什么自成一套：压在画面上要自带对比

这两颗和手柄上的 A/B/X/Y **不**读同一组 `--pad-*`。手柄按键落在近黑的页面底上，
半透明浅灰描边够用；这两颗落在**游戏画面**上，底下是什么颜色没人知道 ——
浅色画面时 `--pad-line`（alpha 0.45 的浅灰）和画面合成后几乎同色，整颗按钮直接消失。

做法是「双色描边」：**外圈一条深色 + 内圈一条浅色**，再配一块深玻璃底。
一个颜色做不到在深浅两种背景上都有 3:1 对比（WCAG 2.2 SC 1.4.11 非文本对比：
控件的边界要能从相邻颜色里分出来，要求 ≥3:1），一深一浅两条则画面亮时外圈起作用、
画面暗时内圈起作用 —— 地图标记和游戏浮层控件就是这么画的。
第二圈只能画在 `box-shadow: inset` 上：再加元素要多套一层 div，`outline` 画在边框外侧
会把圆角甩在脑后（出处：MDN「box-shadow」的 inset 一节，阴影画在边框的内边缘）。

底必须是深色：「菜单」两个字和全屏图标都是浅色，压在浅灰玻璃上等于压在画面上，
浅色画面里字比轮廓先消失。整体透明度从 0.6 提到 0.85：0.6 是把每一层的对比一起乘下去，
描边和字同时变糊，「不抢画面」就变成了「看不见」。

四档颜色写在按钮自己身上（`--btn-ring-out / --btn-ring-in / --btn-face / --btn-face-press`），
不进 `:root`：和手柄材质共享没有意义，改了也不该牵连方向键与动作键。
合成后的对比度实测见 `doc/color.md`，由 `verify-screen-menu-btn` 现算现验
（拿 A 键的 `--pad-*` 当对照组，算出它在白画面上确实 <3:1，说明这套选择不是随手改色）。

按下态必须在这里写全（底 + 外圈 + 内圈）：`.touch-btn:active` 那条会把底换成半透明强调青、
外圈换成亮青，压在浅色画面上会发白 —— 按下这一下反而看不见按钮，反馈就成了负反馈。

### 摆位与几条必须留意的写法

位置与排布始终不变，**都不随菜单关闭而消失** —— 所以它们放在 `.screen` 内而不是 `.sys-ui` 内
（`.sys-ui` 菜单关闭时会 `hidden`）。形状跟着屏幕里的界面元素（小圆角方块，不跟手柄的圆片），
大小跟着画面缩放。

摆位用一个跨规则的量：`.screen` 上定义 `--menu-btn-inset`（距右边缘）、`--menu-btn-size`
（边长，两颗同值）、`--topbar-btn-gap`（按钮之间、文字到按钮，同一个间隙），
顶栏的右内边距 `--topbar-menu-slot` 由这三个数算出来。
这样「徽标右边缘到全屏按钮左边缘」按构造就是 `--topbar-btn-gap`，
不会因两处各改各的而错位（`verify-topbar-align` 盯着它）。
几个必须留意的写法：

- 选择器写成 `.screen .touch-menu` 而不是 `.touch-menu`：`.touch-btn` 的 `width: 3rem`
  声明在后面，同优先级会后声明胜出，多一级才压得住。
- 位置和尺寸必须同一套基准（`--screen-font`），不能一个跟视口缩放、一个用 `rem`。
- `:active` 的 `transform` 要整条重写（`translateY(-50%) scale(0.92)`），它不叠加。
- 描边粗细仍然读 `--pad-line-w`（和手柄同档），只有颜色这一处不共享。
- **全屏按钮不许带 `data-action`**：`app.js` 会把触摸区里 `[data-action]` 的元素逐个绑成动作键，
  写上就等于多一颗往游戏里送按键的按钮。菜单按钮走 `pointerdown`（`input-manager` 绑的），
  全屏按钮靠原生 `click`，所以它必须进长按抑制的例外名单，否则手机上点了没反应。
- **全屏按钮不许带 `data-action`**：`app.js` 会把触摸区里 `[data-action]` 的元素逐个绑成动作键，
  写上就等于多一颗往游戏里送按键的按钮。菜单按钮走 `pointerdown`（`input-manager` 绑的），
  全屏按钮靠原生 `click`，所以它必须进长按抑制的例外名单，否则手机上点了没反应。

「菜单」这颗的语义是确定的「回到游戏」：在子菜单里按它也是关闭全部菜单，
不像 Esc 那样只退一级（按钮上写着「关闭菜单」，只退一级会让人以为没生效）。

## 全屏

- **桌面**：`document.documentElement.requestFullscreen()`，铺满窗口，不锁方向。
- **触屏设备**（`matchMedia('(pointer: coarse)')`）：全屏成功后再
  `screen.orientation.lock('landscape')`，手机直接躺横。锁不上不算失败 ——
  全屏已经成了，补一句「没能自动横屏，请手动把手机转过来」。

对标（结论写在 `app.js` 的注释里）：

- **MDN《Element.requestFullscreen》**：进入全屏要求「瞬时用户激活」（transient activation），
  所以只能在 `click` 回调里直接调用，不能挪到定时器或异步链后面。
- **MDN《ScreenOrientation.lock》**：方向锁通常只在移动设备上、且处于全屏时才允许，
  否则抛 `SecurityError`；不支持的朝向抛 `NotSupportedError`。
- **W3C《Screen Orientation API》**：退出全屏时规范自动解开方向锁，所以不用补 `unlock()`。
- **caniuse「fullscreen」**：iPhone Safari 没有元素全屏（iPad 有）。所以 `catch` 里按
  `e.name === 'NotSupportedError'` 报「这个浏览器不支持全屏」，而不是让人对着没反应的按钮猜。
- **状态以 `fullscreenchange` 为准**：用户还能按 Esc 或安卓返回键退出全屏，那条路只有这个事件
  会通知页面。按钮的图标（Feather 的 maximize / minimize）和 `aria-label` 都在这个事件里切。

## 提示：菜单底栏与 toast

两种提示，各归各处，游戏画面下不留任何常驻条：

- **底栏（`.sys-hintbar`）是菜单的一部分**，一行两栏：左边 `.sys-count` 写「这一列有多少项」
  （「9 款」，没得说就整块 `hidden` 不占位），右边 `.sys-hints` 写「在这个菜单里现在能按什么」。
  两边都是 `.sys-ui` 的子元素、排在列表下面，菜单关掉整栏跟着消失，不需要谁手动清空。
  数量说的是当前这一列列表，读它的时候眼睛本来就在列表和底栏之间；顶栏右端已经有两颗
  常驻按钮，再挤一段文字就是窄栏里三个元素抢位置，所以数量放左下角而不是顶栏。
- **同一屏的提示随焦点变**：焦点在分类栏时写「↑ ↓ 选分类 · A → 进入 · B 关闭菜单」，
  进列表后写「↑ ↓ 选择 · A 确认 · ← B 回分类」。所以 `model.hints` 可以是 `(focus) => [...]`。
  `count` 同理可以是按当前分类给文案的函数 —— 只有焦点在「游戏」栏时才写「9 款」，
  停在别的分类上就空着，别的分类下面没有 9 款游戏，写着就是在说假话。
- **系统提示（`#toast`）是一次性的**。「已保存到槽位 3」「加载失败: …」这类事件性文案
  出现在画面顶部居中的小药丸里，演完自己消失并清空文案（留着会让人误读成当前状态），
  连发新消息直接顶掉旧的。
- **两档时长**：例行回执 2.8 秒；报错、没做成、有意外副作用的走 `showError()` 停留 6 秒 ——
  这类消息错过就查不出来了。哪条算重要由**调用点自己说**（`showError(...)` 或
  `showToast(msg, { important: true })`），不去猜文案：猜「含『失败』二字就算报错」，
  改一次措辞就悄悄失效。跨模块回调（`NesConsole` 的 `onStatus(msg, important)`）把标记一起传出来。
  时长是 CSS 的 `--toast-ms` / `--toast-ms-long`，`.toast-important` 只换动画时长。

几个刻意的选择：

- **toast 挂在 `.screen` 上而不是 `.sys-ui` 里**：菜单关着时它还得能弹出来，
  菜单开着时也要看得见，所以 `z-index: 20` 压在 `.sys-ui`（15）之上，并且 `pointer-events: none`。
- **位置在顶部而不是底部**：底部在手机上会被虚拟手柄叠住。
- **长文案换行，不用省略号截断**：报错要把「哪儿失败了、怎么修」说完，一行放不下。
- **计时写在 CSS 里**（动画演完即收），JS 只换文案并重播动画。没有 `setTimeout`，
  也就没有「新消息被上一条的定时器提前收掉」这类坑。

## 一级菜单最后两栏：操作说明 / 关于

这两栏必须在菜单里：按键说明和核心署名出口都得在屏幕内可达（画面之外只剩触摸手柄），
否则用户没有地方查按键、也没有给上游的署名出口。

- **「操作说明」的键位是现读的**，不是抄一份写死的表：那一栏的每行右边显示的是
  `input.getBindings()` 里的当前绑定（和「按键映射」同一个来源）。所以用户把 A 键改绑成
  `KeyJ` 之后，操作说明立刻跟着写 `J` —— 写死的说明在第一次改绑后就变成假信息，
  比没有说明更糟。
- **「关于」里的 Powered by 是一行可按的条目**：按 A 打开 fceumm 项目主页
  （`https://github.com/libretro/libretro-fceumm`，核心是 GPL-2.0 的，署名出口必须给它），
  行上的次要文字直接写明「按 A 打开项目主页」，不靠用户猜。用
  `window.open(url, '_blank', 'noopener')`，带 `noopener` 才不会让外站拿到 `window.opener`。

## 长按不被当成一个操作（除游戏画面）

手机上按住不放，Android Chrome 会做两件事：派发 `contextmenu`（长按菜单）并**震一下**
表示「识别到长按」。菜单会吃掉后续的 `pointerup` —— 表现是「按键卡在按下状态、
游戏里一直往前跑」；震动那一下出自手势识别阶段，**早于页面拿到任何事件**，
所以只拦 `contextmenu` 是「菜单不弹了但还震」。四层一起才拦得住：

- `document` 上拦 `contextmenu`（CSS 拦不住这个事件）
- `user-select: none`：选不中文字，长按没有「复制」可给
- `-webkit-touch-callout: none`：iOS 的长按气泡（**Chromium 在解析阶段就把它丢了**，
  所以只能在构建出的 CSS 文本里验）
- **非 passive 的 `touchstart` 里 `preventDefault()`**：浏览器不再把这串触摸编成长按手势，
  震动随之消失（真机实测有效）。`touchstart` 在 `document`/`body` 上默认是 passive 的，
  那种监听里 `preventDefault()` 会被直接忽略，所以必须显式写 `{ passive: false }`

最后这条有代价：取消 `touchstart` 会连带吃掉这次触摸的兼容鼠标事件，实测**菜单行的手指点击会失效、
列表也滑不动**（`agent-workspace/probe-longpress-scope.cjs` 量的），所以这三处留了例外 ——
`.sys-ui`（菜单，靠 `click` 和滑动工作）、`#layout-editor`（摆放模式的两个按钮）、
以及按需求保留原生长按的 `canvas` + `#canvas-overlay`。
**例外是按「谁监听 click」划的，不是按位置划的**：虚拟手柄的键虽然能浮到画面上方，
事件的目标仍是键本身，所以照样不震。例外之外的地方长按仍会震一下。

页面里没有任何文本输入框，所以禁选中没有副作用。
