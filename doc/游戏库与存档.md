# 游戏库与存档

两条数据链：**内置游戏怎么进列表**（构建期，文件系统 → 清单），
**存档怎么落库**（运行期，浏览器 IndexedDB）。

## 内置游戏：构建时扫目录

**规则一句话**：把 `.nes` 文件放进 `public/rom/`，重新 `npm run dev` 或 `npm run build`，
它就出现在游戏列表里，标着「内置」。

为什么不能「运行时扫目录」：浏览器不能列出服务器上的目录（没有这种 API，
静态服务器默认也不给目录清单）。所以「有哪些游戏」这件事只能在**构建时**数一遍，
把结果写成一份清单文件，前端去读那份清单。对标 Astro 自己的 Content Collections、
Jekyll 的 `_data`：都是「构建时扫目录 → 生成数据文件 → 运行时只读数据」，静态站没有第二条路。

链路（三个文件）：

1. `src/integrations/rom-catalog.js` —— Astro 集成，在 `astro:config:setup` 钩子里
   扫 `public/rom/*.nes`，写出 `public/games.json`，每条是 `{ id, name, url, size }`。
   `id` 是 ROM 的内容哈希（用 `storage.js` 里那个函数算的，存档也按它存，
   所以清单里的哈希和运行时算的必须一模一样 —— 直接 import，不复制实现）。
   显示名取文件名（去掉 `.nes`），按中文名排序；同一份 ROM 换名字放两份只留一条。
   **做成集成而不是 npm 的 prebuild 脚本**：CI 走的是 `npx astro build`，不经过 npm 脚本，
   挂在构建流程上才能不管谁调用都刷新清单。
2. `public/games.json` —— 生成物，随站点一起发布，但**不入库**：它是上面那个目录的派生物，
   任何 `dev` / `build` 都会重写，而且它按文件名列出镜像里的每一款。
3. `src/lib/game-manager.js` 的 `loadBuiltIn()` —— 启动时 fetch 清单，把每条变成游戏对象。
   清单里的 `id` 就是哈希，所以**没进过游戏也能按哈希查它的存档**，
   也不用为了知道哈希把 2MB 的 ROM 先下载一遍。

想给某款游戏补中文译名、年份、类型、发行商、简介：改 `game-manager.js` 里的 `BUILT_IN_META`，
键用 ROM 的内容哈希（进这款游戏后在「菜单 → 游戏信息」里能看到它的「内容标识」）。
用哈希而不是文件名做键，是因为给文件改名不用回来改这里；反过来，换了一个 dump（内容变了）
就得重新补一条 —— 那已经是另一份文件了。

## 哪些卡带进仓库

`public/rom/` 是开发者的本机卡带镜像，默认**整目录不入库**（`.gitignore` 里 `public/rom/*`），
只按文件名放行一张演示卡带 —— 站点是给人试玩的，打开没游戏就没人会专门去找 ROM 来试。
往这个格里放东西等于随仓库公开分发，是个**发布决定**：只放自制的、公有领域的，
或确认有权分发的卡带。

换成别的演示卡带：把 `.gitignore` 里那行 `!public/rom/…` 改成要放行的文件名，重新构建。
自己玩但不发布的卡带留在本地，走「游戏管理 → 加入游戏」或直接把文件拖进页面
（存 IndexedDB，不进站点）。

## 卡带和测试是绑在一起的

回归脚本按名字点卡带 —— 多数端到端脚本用 `Destiny of an Emperor`
（`smoke-e2e`、`verify-audio-fix`、`verify-dpad`、`verify-pause-on-menu`、`verify-ozone-colors`），
兼容矩阵用 `金庸群侠传` / `重装机兵` / `热血格斗`（`verify-wasm-core`），
`verify-input-reaches-core` 默认也打 `热血格斗`。所以增删 `public/rom/` 之后先跑
`node agent-workspace/run-regression.cjs wasm`：矩阵少一款就补一款，也别留着跑不到的款。
下架某张卡带时，fceumm 认不认那块板子的**结论**留在
`agent-workspace/note-fceumm-wasm.md` 的探针表里，不跟着卡带一起扔。
只带一张演示卡带克隆下来跑全量，会看到「清单里找不到这款」的失败 —— 那是靶子没到位，不是产品坏了。

## 存档：IndexedDB 三张表

库名 `nes-console`，版本 3：

- `savestates` —— 即时存档，内容是不压缩的 RASTATE 字节串，key 是 `内容哈希_槽位`，
  槽位为「自动存档 + 槽位 0~9」。
- `sram` —— 电池存档（游戏自己写的那份进度），按 ROM 内容哈希存一份镜像。
- `roms` —— 从本机文件加入的 ROM 字节，key 是内容哈希；页面加载时由 `games.restoreROMs()`
  灌回游戏列表 —— 没有这张表，加入的游戏刷新一次就没了。

两份存档的分工对标 RetroArch 的 `.state` 与 `.srm`：

- **即时存档里已经包含电池 RAM**：RASTATE 装的是整机内存快照，读档会连带把游戏进度回滚到那一刻。
  这是格式决定的，不是 bug。所以落盘顺序有讲究：**读档之后要把内存里最新的 SRAM 镜像写回库里**
  （`app.js` 的 `persistProgress()`），否则下次开机看到的是上一次自动存档的进度。
- **SRAM 什么时候写**：退出到菜单、页面切到后台、关页面（`beforeunload`）三处，
  跟「自动存档」那个设置无关 —— 那是即时存档的开关，不该顺手关掉真机意义上的进度保存。
- **没有电池 RAM 的板卡不是错误**：`retro_get_memory_size(SAVE_RAM)` 回 0（比如热血格斗），
  这时库里那份 sram 镜像是历史遗留，载入时直接跳过，不报「存档异常」。

其它要点：

- **换端口/域名等于换一份存档**：IndexedDB 按「协议 + 域名 + 端口」隔离。反过来，
  只要还能在列表里看到以前存的档，就说明读的还是同一个库，
  存档看不到/读不出跟服务器怎么起没关系。
- **存档里不写 ROM 数据**：核心序列化出来的是主机内存快照（约 13~22 KB，按板卡而定），
  ROM 本体由 `roms` 表或 `public/rom/` 提供，恢复时内存里本来就有。
- **体积在写入时算好存成 `bytes` 字段**：列槽位只要这一小段元数据，
  不必为了显示大小把整份存档读进内存。
- **切槽位**：呼出菜单后把光标停在「保存存档」或「读取存档」任一行，按 ← / → 在
  「自动存档 / 槽位 0~9」之间循环，两行共用同一个当前槽位（在一行上换，另一行跟着显示同一个）。
  游戏中直接按 ←→ 是 NES 的方向键，不会换槽位。
- **槽位操作是一屏子菜单，不是一行多义**：「存档管理」里空槽位按 A 直接存进去；
  有存档的槽位按 A 进「槽位操作」，里面是「读取存档 / 覆盖保存 / 删除存档」三行，
  删除还要再确认一次。只有 A/B 的手柄要能走到每一步，所以不在一行上挂多个键。
- **从「游戏管理 → 管理存档」也能读档**：这时候游戏并没有在运行，而存档状态只有装着同一个 ROM
  的模拟器才能恢复，所以列表里点槽位会先把这款游戏启动起来再读，不是丢一句「请先启动游戏」。
  同一屏还要能列出没进过的游戏的存档：内置游戏的 `hash` 由构建时扫目录算好写进清单，
  所以列存档不用先把 ROM 下载一遍，也不能拿「有没有 hash」当「有没有存档」。
- **读档失败要说清原因**：存档字节被截断或不是这个核心能吃的格式时，`retro_unserialize`
  直接回失败，宿主抛「核心拒绝了这个存档（可能不是同一款游戏或同一个核心版本）」，
  界面把它拼成一条重要 toast `读取失败: …`，而不是笼统一句「读取失败」。
- **升级核心会让已有即时存档作废**：换核心时存档格式整个换掉（JSON → RASTATE 字节串），
  按项目规则不做兼容层、不做迁移，库升到 v3 时直接重建 `savestates`，旧存档全部作废。
  同一款游戏换了一个核心版本同理 —— 核心自己会拒绝，界面上说清原因。
